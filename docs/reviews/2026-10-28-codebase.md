## Verdict

The REST client wraps 142 endpoints, and the most used paths work: sign-in, listing with a filter, chunked publish, download. Behind them are four kinds of trouble.

1. **Security.** The Vizportal client accepts any TLS certificate on every request, so the session token goes to whoever answers (F1). Ids, tag names and site names are pasted into URL paths, and `System.Uri` collapses `..`, so a call can DELETE a different resource: `DeleteDataSource(session, "../users/U1")` removes a user from the site (F2). The session token and the sign-in password follow redirects to other hosts (F3).
2. **Endpoints that do not do what they say.** The API version and on-premise gates never run (F4). View-data filters are silently dropped (F5). Filter expressions are not URL-encoded (F6). Revision paging is ignored and metadata lists stop at 100 (F7, F8). Schedule "updates" create new schedules, schedule creates throw after succeeding, and two task and one group method call the wrong path or crash every time (F9 to F13).
3. **Today's Tableau, Cloud in particular.** One unknown enum value fails a whole response, and `authSetting="OpenID"` already does (F14). Status codes must match exactly, so Cloud's subscription create fails on success (F15). Nothing in the code knows Server from Cloud, and the client silently caps the API version at 3.14 (F16).
4. **2018 plumbing and API shape.** Downloads are buffered in memory under a 2-minute timeout (F17). Every call builds a new HttpClient and TCP connection, with no way to inject one (F18). There are no retries or 429 handling (F19), lists come back as null (F20), cancellation is a nullable token and missing from Vizportal (F21). The names, parameter orders and return shapes are inconsistent (F22), and the generated xsd types are the public contract (F23). `main` already breaks 1.2.5 while still versioned 1.2.5 (F24), the repo lacks a license and README (F25), and the tests do not build (F26).

2 findings are blockers, 24 are major.

What to fix first:
- **Before any release, even a 1.x patch:** turn TLS validation back on in Vizportal (F1), validate and escape every path segment (F2), and stop following cross-host redirects (F3).
- **Cheap correctness fixes that can ship in a 1.x patch without signature changes:** F5, F6, F7, F10 (status code and time format), F11, F12, F14 (add `OpenID`), F15, F27, F39.
- **Decide the v2 shape in one issue before the modernization starts,** because most other findings land in it: the HttpClient and DI seam (F18), cancellation (F21), naming and return shapes (F22), public models (F23), target frameworks and the version line (F24).
- **Put the test seam in first** (F18, F26), so that every fix above comes with an offline test.

## Findings

Order: blocker (F1, F2), then major (F3 to F26), then minor (F27 to F46), then nit (F47 to F50). Every finding has status **open**.

### F1. Vizportal disables TLS certificate validation for every request, so the session token goes to any server that answers
- **Severity:** blocker (security) · **Anchor:** `Tableau.Api/VizPortal/VizPortalClient.cs:47`
- **Problem:** `buildClient` sets `ServerCertificateCustomValidationCallback = (...) => true` unconditionally. The guard `//if (_tableauApiClient.IgnoreSSLErrors)` on line 46 has been commented out since the first Vizportal commit (`e19a822`, 2023-05-15). Every Vizportal request sends the REST session token as the `workgroup_session_id` cookie (line 33). The REST client, by contrast, validates certificates unless `IgnoreSSLErrors` is set.
- **Failure scenario:** a client on a hostile network (hotel Wi-Fi, a compromised proxy) calls `client.VizPortal.QueryUsers(session)` against `https://tableau.corp`. An attacker presents a self-signed certificate. The handshake succeeds, and the attacker receives the session token and can act as that user (often a site or server admin) until the token expires.
- **Fix:** remove the callback. Honour `IgnoreSSLErrors` (renamed, see F38) in one place shared by both clients. Add an offline test that the handler has no validation callback unless opted in.
- **Breaks public API:** no.
- **Verified:** probe. A TLS server with an untrusted certificate for `CN=untrusted-attacker` on 127.0.0.1: the REST client with `IgnoreSSLErrors = false` failed with `RemoteCertificateNameMismatch, RemoteCertificateChainErrors`. The Vizportal client on the same client object connected, and the server received `Cookie: workgroup_session_id=TOKEN123; XSRF-TOKEN=...`.

### F2. Ids, tag names and site names go into URL paths unescaped, and `System.Uri` collapses `..`, so a DELETE can land on another resource
- **Severity:** blocker (security, data integrity) · **Anchor:** `Tableau.Api/TableauApiClient.cs:135`
- **Problem:** every method interpolates its arguments straight into the path (`$"sites/{session.SiteId}/datasources/{datasourceId}/tags/{tag}"`), and `buildUri` hands the string to `new Uri(...)`. `System.Uri` compresses `.` and `..` segments, also when written as `%2e%2e`. It treats `#` as the start of a fragment and `?` as the start of a query, and leaves `/` as a separator. Affected: every REST method that takes an id builds its path this way. Tag names reach `DeleteTagFromDataSource`, `DeleteTagFromView` and `DeleteTagFromWorkbook`, and site names reach `QuerySiteByName` and `DeleteSiteByName`.
- **Failure scenario:**
  - An app passes a datasource id from a form field: `DeleteDataSource(session, "../users/U1")` sends `DELETE /api/3.14/sites/SITE1/users/U1`, which is Remove User from Site, with the app's (often admin) session.
  - With no malice at all, `DeleteTagFromWorkbook(session, wb, "C#")` sends `DELETE .../workbooks/W1/tags/C`: it removes tag `C` if the workbook has one, and never removes `C#`.
  - `DeleteTagFromDataSource(session, "D1", "..")` and `"%2e%2e"` both send `DELETE .../datasources/D1/`. Whether Tableau routes a trailing-slash path to Delete Data Source is (unverified).
  - `QuerySiteByName(session, "Sales/EMEA")` sends `GET /sites/Sales/EMEA?key=name`.
- **Fix:**
  - Build paths from segments with one helper that validates and escapes each one.
  - Ids: LUIDs are GUIDs, so check them against a strict pattern and throw `ArgumentException` otherwise.
  - Names and tags: reject `.` and `..` (escaping does not help, because `Uri` un-escapes `%2E`), then `Uri.EscapeDataString` the rest, which escapes `/`, `#`, `?` and `%`.
  - Add data-row tests with `..`, `%2e%2e`, `C#`, `a/b`, `a?b` and `100%` for every method that takes a name.
- **Breaks public API:** no signatures change. Inputs that used to be sent raw now throw or are escaped, so say so in the release notes.
- **Verified:** probe against the fake server, for every example above. Request lines as recorded: `DELETE /api/3.14/sites/SITE1/users/U1`, `DELETE /api/3.14/sites/SITE1/workbooks/W1/tags/C`, `DELETE /api/3.14/sites/SITE1/datasources/D1/` for both `..` and `%2e%2e`, `GET /api/3.14/sites/Sales/EMEA?key=name`.

### F3. The session token and the sign-in password follow redirects to other hosts
- **Severity:** major (security) · **Anchor:** `Tableau.Api/TableauApiClient.cs:124`
- **Problem:** the handler has `AllowAutoRedirect = true`, and the token is put into `DefaultRequestHeaders` (line 130). .NET strips `Authorization` on a redirect, but not custom headers such as `X-Tableau-Auth`. A 307 or 308 also replays the POST body. The Vizportal handler follows redirects too (`VizPortalClient.cs:45`); its cookies are scoped by domain, so they do not leak.
- **Failure scenario:**
  - A load balancer, a misconfigured hostname change or an open redirect answers `302 Location: https://other-host/...`. The next request carries `X-Tableau-Auth: <token>` to `other-host`.
  - A `307` on `POST auth/signin` sends `<credentials name="admin" password="...">` to the other host.
- **Fix:** set `AllowAutoRedirect = false` and treat a 3xx as an error, or follow only same-origin redirects in a `DelegatingHandler`. Put the token on each `HttpRequestMessage` rather than on `DefaultRequestHeaders`. Add an offline test with a redirecting fake server.
- **Breaks public API:** no. Behaviour change: cross-host redirects now fail.
- **Verified:** probe. A server on `127.0.0.1` redirected to `localhost` on another port. The second server received `GET /collect` with `X-Tableau-Auth='TOKEN123'`, and after a 307 on sign-in it received `POST /collect-signin` whose body contained the password.

### F4. The API version gate and the on-premise gate never run, and the obvious fix would crash the type and block Tableau Server too
- **Severity:** major (correctness) · **Anchor:** `Tableau.Api/TableauApiClient.cs:37`
- **Problem:**
  - The static constructor builds `_minVersionForEndpoints` and `_onPremiseOnlyEndpoints` from `typeof(TableauApiClient).GetProperties()`. But `[ApiVersion]` and `[OnPremiseOnly]` sit on methods, so both tables are empty, and `checkEndpointAvailability` (lines 113 to 120) never throws. Every `TableauApiVersionException` and `TableauOnlineNotSupportedException` documented in the XML docs of most methods is dead.
  - Switching to `GetMethods()` would make `ToDictionary` throw on the duplicate names `CreateHourlySchedule` and `UpdateToHourlySchedule` (two overloads each). In a static constructor, that is a `TypeInitializationException` on first use of the client.
  - The on-premise branch throws whenever the method is listed. It never asks whether the server is Cloud, so once it runs, `SwitchSite` and all 13 schedule methods would throw on Tableau Server.
  - The private `createSchedule` and `updateSchedule` call the check with their own names.
- **Failure scenario:** a client built with `apiVersion: "2.0"` calls `SignInWithPAT` (gated at 3.7). Instead of `TableauApiVersionException`, it sends `POST /api/2.0/auth/signin` with the PAT, and the caller gets whatever error the server returns.
- **Fix:** replace reflection with an explicit `EnsureApiVersion(3, 7)` call at the top of each method, or a source-generated table keyed by method, not by name. Run the Cloud check only when the client knows it talks to Cloud (F16). Add one test per public method: a lower version throws and sends no request.
- **Breaks public API:** no signature change. Behaviour change: calls start throwing before sending. Making the two attribute types internal would be a break.
- **Verified:** probe. Reflection read `_minVersionForEndpoints.Count=0` and `_onPremiseOnlyEndpoints.Length=0`. There are 142 public methods with `[ApiVersion]` and 21 with `[OnPremiseOnly]`. `ToDictionary` over the methods threw `An item with the same key has already been added. Key: CreateHourlySchedule`. `SignInWithPAT` and `SwitchSite` on a 2.0 client both reached the fake server.

### F5. `QueryViewData` strips the `vf_` prefix, so view filters are not sent as filters and unfiltered data comes back
- **Severity:** major (correctness, security) · **Anchor:** `Tableau.Api/TableauApiClient_WorkbooksAndViews.cs:149`
- **Problem:** `QueryViewData` removes a leading `vf_` from every filter name (lines 148 to 151), while `QueryViewImage`, `QueryViewPDF` and `QueryViewCrosstabExcel` add it. Tableau documents `GET .../views/{view-id}/data?vf_<fieldname>=<value>` (example `/data?vf_year=2017`). Names that never had the prefix are sent raw too. This has been the code since the first commit (`934c618`, 2018).
- **Failure scenario:** an app exports per-customer CSVs with `QueryViewData(session, viewId, null, ("vf_Customer", "ACME"))`. The request is `.../data?Customer=ACME`, which is not a filter in Tableau's documented syntax, so the view's full data comes back. How Tableau treats the unprefixed parameter is (unverified). If the filter was the only thing scoping the export, other customers' rows leak.
- **Fix:** add the `vf_` prefix exactly as the image, PDF and crosstab methods do, with an ordinal comparison (F28). Add `maxAge`. Share one filter-building helper across the four methods.
- **Breaks public API:** no. Behaviour change that callers want.
- **Verified:** probe and docs. `QueryViewData(..., ("vf_Region","West"))` sent `.../data?Region=West`, while `QueryViewImage(..., ("Region","West"))` sent `.../image?vf_Region=West`. The docs page says Query View Data filters use the `vf_` prefix.

### F6. Filter and sort expressions, and every query-parameter name, are sent without URL encoding
- **Severity:** major (correctness) · **Anchor:** `Tableau.Api/TableauApiClient.cs:137`
- **Problem:** `buildUri` encodes values with `HttpUtility.UrlEncode`, except when the key is `filter` or `sort`. Keys are never encoded. Filter values are user data (names, emails, tags), and `&`, `#`, `+` and `%` change the meaning of the URL. The view-filter field names in F5 are keys, so `R&D` splits the query too.
- **Failure scenario:**
  - `QueryDataSources(session, filterExpression: "name:eq:R&D")` sends `...&filter=name:eq:R&D`. The server sees the filter `name:eq:R` plus a stray parameter `D`, and returns the data sources named `R`.
  - `GetUsersOnSite(session, filterExpression: "name:eq:C++")` sends `C++` raw, which query decoding usually reads as `C` followed by two spaces.
  - A `#` in a value cuts the URL off at that point.
- **Fix:** escape every key and value with `Uri.EscapeDataString`. For `filter` and `sort`, add a small typed builder (`Filter.Eq("name", "R&D")`, `Sort.Asc("name")`) that escapes each value and keeps `:` and `,` as syntax. Keep the string overload, escaping the parts between the separators.
- **Breaks public API:** no. Callers who pre-encoded their filter strings would get double encoding, so say so in the migration guide.
- **Verified:** probe. The recorded request lines were `GET /api/3.14/sites/SITE1/datasources?pageSize=100&pageNumber=1&filter=name:eq:R&D`, `.../users?pageSize=100&pageNumber=1&filter=name:eq:C++` and `.../views/V1/data?R&D=x+y`.

### F7. `GetDataSourceRevisions` and `GetWorkbookRevisions` validate `pageSize` and `pageNumber` but never send them
- **Severity:** major (pagination) · **Anchor:** `Tableau.Api/TableauApiClient_Revisions.cs:39`
- **Problem:** both methods range-check the paging arguments and then call `buildUri(...)` with no parameters (lines 39 and 65). Tableau documents `?pageSize=&pageNumber=` for both.
- **Failure scenario:** a workbook has 250 revisions. A caller loops over pages 1 to 3 and gets page 1 three times: revisions 101 to 250 are never seen. A loop that runs until it gets an empty page never ends.
- **Fix:** pass `("pageSize", ...)` and `("pageNumber", ...)` as the other list methods do, and add an offline test that asserts the query string.
- **Breaks public API:** no.
- **Verified:** probe and docs. `GetDataSourceRevisions(session, "D1", pageSize: 10, pageNumber: 3)` sent `GET /api/3.14/sites/SITE1/datasources/D1/revisions`, with no query string.

### F8. `QueryDatabases` and `QueryTables` return only the first page and throw away the pagination element
- **Severity:** major (pagination) · **Anchor:** `Tableau.Api/TableauApiClient_Metadata.cs:33`
- **Problem:** both return a bare array and take no paging arguments (lines 33 and 88). Tableau's documented Query Databases response carries `<pagination pageNumber="1" pageSize="100" totalAvailable="496">`, so the list is paged at 100.
- **Failure scenario:** a site with 496 databases: `QueryDatabases` returns 100 and gives the caller no way to know that 396 are missing, or to ask for them.
- **Fix:** return `(paginationType, T[])`, or better the paged shape from F22, and accept `pageSize` and `pageNumber`. The docs list no paging parameters for Query Databases (Query Tables was not checked), so whether the server honours them is (unverified). The response is paged either way.
- **Breaks public API:** yes, the return type changes. Add new overloads and obsolete the old ones in 1.x if a patch is wanted.
- **Verified:** read the code. The docs example response for Query Databases shows the pagination element. Query Tables was not checked in the docs.

### F9. `UpdateTo*Schedule` creates a new schedule instead of updating one, and has no schedule id to update
- **Severity:** major (correctness: wrong endpoint and verb) · **Anchor:** `Tableau.Api/TableauApiClient_JobsTasksSchedules.cs:349`
- **Problem:** the private `updateSchedule` is a copy of `createSchedule`: `POST schedules`. Tableau's Update Schedule is `PUT /api/{v}/schedules/{schedule-id}`. None of the five public `UpdateTo*Schedule` methods (seven overloads in all, counting the two hourly ones) takes a schedule id.
- **Failure scenario:** a maintenance script calls `UpdateToDailySchedule(session, "Nightly", 50, ...)` to move "Nightly" to 02:00. Tableau creates a second schedule (or rejects the duplicate name), the original stays unchanged, and the caller gets an exception for status 201 (F10).
- **Fix:** add `UpdateScheduleAsync(session, scheduleId, ...)` sending `PUT schedules/{id}`, with only the fields given. Mark the `UpdateTo*` methods `[Obsolete]` with the error flag in 1.x, and remove them in 2.0.
- **Breaks public API:** yes, it needs a new parameter. Add a new method and obsolete the old ones.
- **Verified:** probe and docs. `UpdateToDailySchedule` sent `POST /api/3.14/schedules`. The docs give `PUT /api/api-version/schedules/schedule-id`, version 2.3, 200.

### F10. `Create*Schedule` expects 200 but Tableau returns 201, sends the time with the machine's UTC offset, and never sends a day for monthly schedules
- **Severity:** major (correctness, culture) · **Anchor:** `Tableau.Api/TableauApiClient_JobsTasksSchedules.cs:105`
- **Problem:**
  - **Status:** `createSchedule` expects 200, and the docs give 201 for Create Schedule. So every create throws `TableauRequestException` (status 201, no details) after the schedule exists.
  - **Time format:** `frequencyDetails.start` is a `DateTime` with `DataType="time"`. XmlSerializer writes it as `HH:mm:ss.fffffffzzz` with the local offset, while the docs ask for `HH:MM:SS`. How Tableau reads the offset is (unverified). A `TimeSpan` of 25 hours wraps to 01:00 without an error (line 119).
  - **Monthly:** the docs require an interval `monthDay="1".."31"|"LastDay"`. `CreateMonthlySchedule` sends an empty `<intervals />`. In 1.2.5 the method took `string dayToRun` and ignored it; commit `62871f9` ("removedWarnings") then deleted the parameter to silence the warning.
- **Failure scenario:** `CreateDailySchedule(session, "Nightly", 50, Extract, Parallel, 18:30)` on a machine at UTC+1 sends `start="18:30:00.0000000+01:00"`. The schedule is created and the call throws. A caller who retries creates it again.
- **Fix:** accept any 2xx (F15). Serialize the time as an invariant `HH:mm:ss` string through a string-typed shadow property in `SchemaExtensions`. Validate `TimeSpan` in `[00:00, 24:00)`. Add `monthDay` to the monthly create and update.
- **Breaks public API:** the status and time fixes, no. Adding `monthDay` to `CreateMonthlySchedule` changes its signature, so add an overload.
- **Verified:** probe and docs. The recorded body was `<frequencyDetails start="18:30:00.0000000+01:00"><intervals /></frequencyDetails>`, and the call threw "HTTP Status Code: 201". The docs say Create Schedule returns 201 and give the `HH:MM:SS` and `monthDay` rules. `git show b23503e` shows that `dayToRun` was unused in 1.2.5.

### F11. `GetExtractRefreshTasks` throws on every call: `InvalidCastException` when there are tasks, `ArgumentNullException` when there are none
- **Severity:** major (correctness) · **Anchor:** `Tableau.Api/TableauApiClient_JobsTasksSchedules.cs:93`
- **Problem:** `resp.task.Where(e => e.Item is taskExtractRefreshType).Cast<taskExtractRefreshType>()` filters on `e.Item` but casts `e`, which is a `taskType`. An empty `<tasks/>` leaves `resp.task` null, so `Where` throws. The analyzers flag all three casts (CA2021), but the build suppresses or ignores them.
- **Failure scenario:** any site with at least one extract refresh task: `InvalidCastException`. A site without tasks: `ArgumentNullException (Parameter 'source')`.
- **Fix:** `(resp.task ?? []).Select(t => t.Item).OfType<taskExtractRefreshType>().ToArray()`, and the same for flows. Drop the `scheduleType` element, or explain what it is meant to hold. Name the tuple elements, or return a dedicated type (F22). Turn CA2021 into an error.
- **Breaks public API:** no for the fix. Changing the tuple would be a break.
- **Verified:** probe. With one `<task><extractRefresh .../></task>`: "Unable to cast object of type 'taskType' to type 'taskExtractRefreshType'". With `<tasks/>`: "Value cannot be null. (Parameter 'source')". CA2021 fired on lines 93, 94 and 95.

### F12. `GetExtractRefreshTask` calls `tasks/{id}`, a path Tableau does not document
- **Severity:** major (correctness: wrong endpoint) · **Anchor:** `Tableau.Api/TableauApiClient_JobsTasksSchedules.cs:71`
- **Problem:** the docs give `GET /api/{v}/sites/{site-id}/tasks/extractRefreshes/{task-id}` (2.6). The code calls `sites/{site}/tasks/{taskId}`.
- **Failure scenario:** every call returns an error from the server, presumably 404 (unverified on a live server).

- **Breaks public API:** no.

### F13. `UpdateGroupFromActiveDirectory` and `UpdateGroupFromActiveDirectoryAsJob` omit the group id
- **Severity:** major (correctness: wrong endpoint) · **Anchor:** `Tableau.Api/TableauApiClient_UsersAndGroups.cs:139`
- **Problem:** both send `PUT sites/{site}/groups`, and neither takes a group id. The docs give `PUT /api/{v}/sites/{site-id}/groups/{group-id}[?asJob=true]`. The plain `UpdateGroup` has the id in its path but does not null-check it (line 116).
- **Failure scenario:** an AD sync job calls `UpdateGroupFromActiveDirectory(session, "Sales", "CORP", Viewer)`. The server rejects a PUT on the collection (status unverified), and the AD group is never synchronized.
- **Fix:** add `groupId` to both methods and the null check to all three.
- **Breaks public API:** yes, it needs a new parameter. Add overloads and obsolete the old ones.
- **Verified:** probe and docs. The recorded request was `PUT /api/3.14/sites/SITE1/groups`. The docs show the group id in the path for both the plain and the AD form.

### F14. One unknown enum value in a response fails the whole call, and `authSetting="OpenID"` already does
- **Severity:** major (correctness, Tableau Cloud) · **Anchor:** `Tableau.Api/Models/XmlSchema.cs:4260`
- **Problem:** the 27 generated enums (and the hand-written `capabilityTypeName`) are closed. XmlSerializer throws `InvalidOperationException` on any value it does not know, and the whole response is lost. Tableau adds values over time. `siteUserAuthSettingType` has `ServerDefault`, `SAML` and a hand-added `TableauIDWithMFA`, while the docs list `OpenID` (Cloud only) as well. The last commit's only code change was adding `TableauIDWithMFA` for this reason.
- **Failure scenario:** `GetUsersOnSite` on a Cloud site where one user signs in with OpenID: "Instance validation error: 'OpenID' is not a valid value for siteUserAuthSettingType". No user on that page comes back. The same happens for any new `siteRole`, `capabilityType` or `scheduleType` value.
- **Fix:** add `OpenID` now. For v2, map enum-valued attributes as strings with a typed accessor that returns `null` for unknown values, or use a tolerant reader. Add fixtures with unknown values to the offline tests.
- **Breaks public API:** adding a member, no. Changing generated properties from enum to string, yes, so plan it with F23.
- **Verified:** probe. A users page with `authSetting="OpenID"` threw the message above. The docs list OpenID and TableauIDWithMFA as Cloud-only values.

### F15. Status codes must match exactly, so Tableau Cloud's subscription create fails after it succeeds
- **Severity:** major (error mapping, Tableau Cloud) · **Anchor:** `Tableau.Api/TableauApiClient.cs:173`
- **Problem:** `apiRequest` throws unless the status equals one expected value. Any other 2xx becomes a `TableauRequestException` with no details. The docs give Create Subscription 201 on Server and 200 on Cloud. The library expects 201 (`TableauApiClient_Subscriptions.cs:38`) and sends the Server body (`<schedule id>`), while Cloud from 3.20 takes `<schedule frequency>` with `frequencyDetails`. F10 is the same problem on Server.
- **Failure scenario:** `CreateSubscription` on Tableau Cloud: if Cloud accepts the Server body (unverified), the subscription is created and the call throws. Either way, there is no Cloud form to call.
- **Fix:** treat any 2xx as success, and keep the expected code only for a debug log. Add a Cloud overload of `CreateSubscription` and `UpdateSubscription` taking frequency details.
- **Breaks public API:** no. The Cloud overload is additive.
- **Verified:** read the code and the docs (subscriptions page: "Cloud: POST ..., returns 200", Cloud form in API 3.20).

### F16. Server and Cloud are not modeled at all, and the client silently caps the API version at 3.14
- **Severity:** major (Tableau Cloud) · **Anchor:** `Tableau.Api/TableauApiClient.cs:29`
- **Problem:**
  - Nothing detects or configures Cloud vs Server. `[OnPremiseOnly]` cannot work without that (F4), and it is wrong on `DeleteGroup`: the docs put no Cloud restriction on it, and give 2.1 where the library gates at 2.0.
  - `_maxVersion = 3.14` turns any requested version above it into 3.14, with only a warning log (lines 72 to 78), while the schema is 3.16 and Cloud forms start at 3.20. A caller who asks for "3.21" to get Cloud behaviour silently gets 3.14 URLs.
  - Cloud-only and Cloud-changed endpoints are missing: Create Cloud Extract Refresh Task (3.20, the Cloud replacement for Add Data Source to Schedule), and the Cloud subscription forms (F15).
  - Impersonation is "Tableau Server only" in the docs, and nothing warns.
  - Session lifetime is 120 minutes on Cloud and 240 on Server (F34).
  - The last commit is titled "tableau cloud hangling changes, tableau server type and checks", but its diff adds one enum member and three lines of notes. There is no server-type code in the repository.

### F17. Every download is buffered in memory under the 2-minute request timeout, and a response without Content-Type crashes
- **Severity:** major (HTTP, memory) · **Anchor:** `Tableau.Api/TableauApiClient_WorkbooksAndViews.cs:446`
- **Problem:**
  - `apiRequest` uses `SendAsync` with the default `HttpCompletionOption.ResponseContentRead` and returns `resp.Content` after the HttpClient is disposed. - **Verified:** probe. A 5,000,000-byte download returned `System.IO.MemoryStream, CanSeek=True, Length=5000000`. A response without Content-Type threw `NullReferenceException`.

### F35. `TableauRequestException` carries too little: no inner exception, method, headers or raw body, a settable status, and an internal constructor
- **Severity:** minor (error mapping) · **Anchor:** `Tableau.Api/Exceptions/TableauRequestException.cs:13`

- **Verified:** read the code.

## Tests

**What exists:** 11 MSTest methods (F26). They need a live Tableau Server, run in name order, and cover 10 of the 185 public methods. Vizportal, permissions, schedules, metadata, downloads, sites, users and groups, favorites, revisions and subscriptions have no test at all.

**What cannot be tested without a server:**
- whether Tableau accepts a given request body (for example the empty `<project/>`, F32);
- real rate limits and token expiry;
- Cloud-only behaviour and MFA or SSO sign-in;
- the chunk size limit;
- everything about Vizportal's semantics.

**What can be tested offline once F18 adds the seam**, which is most of the 6,800 hand-written lines, all request building and response parsing:
1. **Seam:** `TableauApiClient(HttpClient, TableauClientOptions, ILogger?)`, with every request going through one internal `SendAsync`.
2. **Fake handler:** a `FakeTableauHandler : HttpMessageHandler` with a route table (method plus path pattern) that returns fixture responses and records every request: method, path, query, headers and body.
3. **Fixtures:**
   - one XML response file per endpoint under `Tableau.Api.Tests/Fixtures/<Area>/<Method>.xml`, taken from the example responses in the Tableau REST API reference;
   - JSON fixtures for Vizportal;
   - golden request bodies next to them.
   An optional recording handler can refresh fixtures from a real server, with tokens scrubbed.
4. **Per-method contract tests**, generated as data rows where possible:
   - verb, path, query string, body against the golden file, and the status handling;
   - the fixture deserializes, and an empty-list fixture returns `[]`.
5. **Cross-cutting tests:**
   - every public method throws `TableauApiVersionException` below its gate without sending (F4);
   - path segments with `..`, `%2e%2e`, `C#`, `a/b` and `a?b` are rejected or escaped (F2);
   - `filter` and `sort` values with `&`, `+` and `#` are escaped (F6);
   - the suite runs under sv-SE, tr-TR and a non-UTC time zone (F10, F28);
   - unknown enum values deserialize (F14);
   - a cross-host redirect does not carry the token (F3);
   - the Vizportal handler has no certificate callback (F1);
   - downloads stream without buffering (F17);
   - paging loops terminate (F7, F8).
6. **Live suite:** a separate test class or category, driven by environment variables (`TABLEAU_URL`, `TABLEAU_SITE`, `TABLEAU_PAT_NAME`, `TABLEAU_PAT_SECRET`) and `Assert.Inconclusive` when they are absent. Each test creates its resources in a GUID-named project and deletes them in cleanup. No test depends on another's order.
7. **Stack:** MSTest 3.x or later on Microsoft.Testing.Platform (MSTest.Sdk), on net10.0, with coverage collected and gated in CI. Package validation against 1.2.5 (F24) runs in the same pipeline.

## A modern shape

A sketch for the 2.0 design issue. Every part maps to findings above.

```csharp
services.AddTableauClient(o =>
{
    o.ServerUrl = new Uri("https://tableau.example.com/");   // path kept (F39)
    o.Deployment = TableauDeployment.Cloud;                   // or detect (F16)
    o.ApiVersion = "3.24";                                     // gate per method (F4)
    o.Site = "finance";
    o.Credentials = TableauCredentials.PersonalAccessToken(name, secret);
})
.AddStandardResilienceHandler();                               // F19

public sealed class TableauClient : ITableauClient             // one HttpClient (F18)
{
    public IAuthClient Auth { get; }
    public IWorkbooksClient Workbooks { get; }
    public IDataSourcesClient DataSources { get; }
    public IViewsClient Views { get; }
    // ... one sub-client per area
}

await foreach (var wb in client.Workbooks.ListAsync(Filter.Eq("name", "R&D"), cancellationToken))   // F6, F7, F20, F21
    Console.WriteLine(wb.Name);

await using var download = await client.Workbooks.DownloadAsync(id, includeExtract: false, cancellationToken);  // F17, F42
```

- **HTTP pipeline:** a typed `HttpClient` from `IHttpClientFactory`. A `TableauAuthHandler : DelegatingHandler` signs in lazily (single-flight), sets `X-Tableau-Auth` per request, signs in again on 401, and refuses cross-origin redirects (F3, F34).
- **Signatures:** `Task<T> XxxAsync(..., CancellationToken cancellationToken = default)` everywhere (F21). Lists come as `IAsyncEnumerable<T>`, and pages as `Page<T> { Items, PageNumber, PageSize, TotalAvailable }` with `int` fields (F22, F23).
- **Models:** hand-written public records with nullable values and `DateTimeOffset`, with the generated DTOs internal (F23).
- **Exceptions:** the hierarchy in F35.
- **Options and state:** immutable options validated at start-up, no static state, no reflection for the gates (F4, F46).
- **Packaging:** `net8.0;net10.0` (plus `netstandard2.0` if needed), Nullable on, analyzers on, package validation against 1.2.5 (F24, F40).
- **Vizportal:** a separate, clearly experimental package (`Tableau.Api.VizPortal`), since it is undocumented, with TLS fixed (F1) and tokens added (F21).

## What to keep

- **Async throughout:** every public method is async, and there are no sync-over-async wrappers in the library.
- **Safe XML parsing:** DTDs are prohibited (the `XmlReader` default). An XXE payload in a response was rejected with "For security reasons DTD is prohibited".
- **No secrets leak:** credentials and tokens stay out of logs and exception messages. In the probe, 0 of 60 log lines contained the password, token or PAT secret. `TableauSession` has no `ToString`, and exception messages contain neither the URL nor the token.
- **REST TLS on by default:** the REST client validates certificates unless the caller opts out.
- **Chunked publish streams:** each chunk goes from the caller's stream without being buffered in memory (`StreamContent` with a known length).
- **Vizportal XSRF:** the double-submit token (a random value as both cookie and header) needs no scraping of a login page.
- **Structure worth carrying into v2:**
  - consistent argument checks (`checkNullParameters`, page-size bounds);
  - one partial file per REST area, which maps cleanly onto sub-clients;
  - XML doc comments copied from the Tableau reference on most REST methods;
  - the `SchemaExtensions` partial-class pattern for hand additions to generated types;
  - Vizportal's `IAsyncEnumerable` paging;
  - encoding query values (extended in F6).
- **Small footprint:** two package dependencies. Serializer start-up is not a problem (58 ms for the first `XmlSerializer`, cached afterwards).

## Not covered

- **Live behaviour:** no Tableau Server or Cloud was available. Server-side behaviour comes from the help.tableau.com REST API reference pages listed at the top, or is marked unverified:
  - how Tableau treats unprefixed view filter names (F5) and empty `<project/>` elements (F32);
  - whether it rejects U+2212 (F28) and how it reads a time with an offset (F10);
  - whether a trailing-slash DELETE reaches the parent resource (F2);
  - whether 401002 is used for every expired session (F34);
  - whether Cloud accepts the Server subscription body (F15);
  - the Content-Type of `.tds` downloads (F42);
  - whether metadata lists accept paging parameters (F8).
- **Vizportal:** there is no Vizportal sign-in on `main`: no RSA password encryption and no login call. The client reuses the REST token as the `workgroup_session_id` cookie. Whether that works on Tableau Cloud, whether Vizportal matches JSON property names case-sensitively (F29), its page caps and enum values (F41), and how it handles `Secure` cookies over HTTP (F49) are all unverified.
- **Docs pages not fetched:** Sites, Projects, Favorites, Permissions and Server Info. Their endpoints are marked "not checked" in the tables.
- **Generated models:** `XmlSchema.cs` was not reviewed line by line. The members of the generated model classes were not diffed between 1.2.5 and `main`, only the types and the client methods. A regeneration may already have changed attribute types that consumers use.
- **NuGet_Prod methods:** the four methods were checked against the docs, not run.
- **Process:** this was a single-reviewer pass. Findings were verified by probes, analyzers, the API dump or the docs as stated in each finding, but not by an independent refuter.
- **Residual risk:**
  - F2 shows that any public method taking a name or id can be steered; the fix has to cover all of them, not only the examples.
  - Until F4 is fixed, the documented exceptions in every method's XML docs are wrong.
  - The `ado-nuget-prod` branch and any remotes were not reviewed beyond the one commit asked for.
